# Stack Upgrade and Import Follow-ups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every dependency and the runtime up to date, the five open points after 0.7.0 closed, and the genericity audit's findings fixed.

**Architecture:** Upgrades first (minors, then each major on its own commit), so the follow-up features are built and tested on the new stack. Cross-process settings invalidation uses Postgres `LISTEN/NOTIFY` through the existing `pg` pool; the other follow-ups are local changes to the AI services, the import wizard and the XLS reader.

**Tech Stack:** pnpm workspace, Next.js 16, React 19, Drizzle + `pg`, pg-boss, vitest, Playwright, `@anthropic-ai/sdk`.

**Spec:** `docs/superpowers/specs/2026-11-24-stack-upgrade-and-import-followups-design.md`

## Global Constraints

- Existing installations keep working after the upgrade: no renamed technical identifiers, no new required environment variable, PostgreSQL server stays 17 (Compose, Helm, CI).
- TypeScript stays on the latest 6.x (`typescript-eslint` supports `<6.1.0`).
- An upgrade that cannot be made to work with reasonable effort is held back to the newest working version and reported, never forced through by weakening tests.
- Every task ends with `pnpm format:check && pnpm lint && pnpm typecheck` and its focused tests green; tasks that touch runtime, dependencies or shared code also run `pnpm test`. Tests run under Node 26 once Task 2 lands (use a local Node 26 binary, first on `PATH`).
- e2e: `pnpm --filter @arfolio/web e2e --trace off` (or `--project=<name>`); the build may stop once at a Next.js upgrade notice: rerun. Never run `next upgrade` or `playwright install` outside what a task says.
- Generic and private: no personal data, no bank/country/language assumptions, strings in all five locales, brand helpers in UI code (AGENTS.md).
- Conventional Commits, `git commit -s`, explicit paths, body ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Do not push.

## Review Focus

1. An installation upgraded in place (existing database, existing env): migrations, roles and the setup flow still work on Node 26 and the new dependencies.
2. A worker or second web replica after an owner removes the API key: no AI request leaves with the removed key once the save has returned.
3. The `pg` LISTEN connection drops (Postgres restart): the process reconnects, and drops its cache on reconnect so a change made while disconnected is not missed.
4. The Anthropic SDK 1.x sends `Authorization: Bearer` and `anthropic-version: 2026-10-21`: every AI path (categorisation, merchants, reports, valuation, PDF import, key test) still works against the e2e fake and unit fakes.
5. An XLS whose shared string table or directory is unusual but valid in other readers is not rejected.

### Task 5: Settings invalidation across processes

**Files:** `packages/services/src/integration-config.ts` (or a new `settings-notify.ts` next to it), `packages/services/src/instance-settings.ts` (notify on write/remove), `apps/web/src/server/integration-config.ts`, `apps/worker/src/index.ts`, tests.

**Interfaces:** `export const SETTINGS_CHANNEL = 'arfolio_settings'`; writes of instance settings run `select pg_notify(SETTINGS_CHANNEL, '')` in the same transaction; `export function listenForSettingsChanges(pool: pg.Pool, onChange: () => void, opts?: { onError?(message: string): void }): { close(): Promise<void> }` holds one dedicated client, `LISTEN`s, calls `onChange` on every notification and after every (re)connect, and reconnects with backoff when the client errors or ends.

- [ ] Tests (real Postgres, as the services tests already use): a write in one pool notifies a listener on another pool; remove notifies; after the listener's connection is terminated (`pg_terminate_backend`) it reconnects and calls `onChange`; `close()` stops reconnecting.
- [ ] Wire it into the web process (invalidate the web cache) and the worker (invalidate the worker cache). The channel name is a technical identifier: document it in `docs/architecture.md`.
- [ ] Commit `fix(settings): drop cached settings in every process when one changes`.
